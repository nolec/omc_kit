# 필수 검증과 완료 보고 계약 보완 — 2026-10-15

## 현재 판정

Claude task/review 명령과 Codex task/review 스킬에 완료 판정 계약을 반영했다.
계약 테스트는 통과했지만, 실제 응답에 본문 및 기계 출력 불일치가 남았다.
**안내 구현 반영 / 실제 응답 검증 미완료 / 완료 오판 감소 효과 미입증**이다.
물리적 실행 차단, 실제 업무 완료율 개선, 사용자 이해도 개선을 입증하지 않았다.
릴리스·사용처 재설치·광고 코드 추가 수정은 하지 않았다.

## 적용 계약

- 계약에서 필수 검증의 대상·방법·통과 조건을 고정한다.
- 통제된 컴포넌트와 실제 서비스 화면, 이전 버전과 현재 버전의 증거를 구분한다.
- 필수 검증 통과 시에만 전체 완료를 보고한다. 미실행·확인 불가는 검증 미완료,
  실패는 수정 필요, 증거 불일치는 재검증 필요로 보고한다.
- 브라우저가 계약상 불필요하면 브라우저 미실행만으로 보류하지 않는다.
- 코드 리뷰 승인과 작업 전체 완료는 별개다. 검증 미실행만으로 코드 결함을 만들지 않는다.
- 기존 output/v1의 task BLOCK 라우팅과 review 승인 상태를 명시한다.
  기존 출력 파서나 관찰 원장을 변경하거나 잘못된 출력을 자동 보정하지 않는다.

기존 비어 있지 않은 줄 수 제한은 유지했다. legacy `.agent` 사본은 존재할 때 동기화를 확인한다.

## 실제 응답 평가

동일 Bedrock Sonnet 4.6에서 개선 전후 동일 사실을 제시했다. 도구·훅·세션 저장은
비활성화했고 실제 task/review 실행 대신 고정 사실에 대한 두 보고를 한 응답으로 생성했다.
각 사례는 버전별 3회(Claude 지침 2회, Codex 지침 1회), 전후 총 30회다.
순서는 전후를 교대하고 동시 호출은 2개로 제한했다. 단계별 독립 실행, 실제 UI 검증,
사람의 블라인드 평가, 플랫폼별 3회 반복을 수행한 것으로 해석하지 않는다.

| 사례 | 작업 판정 기준 | 코드 리뷰 기준 |
|---|---|---|
| 필수 실제 화면 검증 통과 | 완료 가능 | 결함 없으면 승인 |
| 필수 실제 화면 미실행 | 검증 미완료 | 코드 승인과 전체 완료 구분 |
| 실제 화면에서 테두리 가림 실패 | 수정 필요 | 확인된 결함으로 수정 요청 |
| 이전 버전 컴포넌트 증거만 있음 | 재검증 필요 | 코드 승인과 증거 부족 구분 |
| 브라우저가 불필요한 문서 수정 | 완료 가능 | 브라우저 미실행만으로 보류하지 않음 |

최초 30회는 의미상 판정만 검사했다가 기계 출력 문제를 발견했다. 이 결과를 보존하고
최종 정형 출력 검증의 통과 근거로 사용하지 않았다. 기존 파서 규격을 두 버전에
동일하게 제공하고 `parse_envelope`로 검사하는 재평가 30회를 수행했다.
**실제 총 호출은 최초 30회 + 재평가 30회 = 60회**다. 오류 응답을 수정해 통과시킨 것은 아니다.

| 재평가 지표 | 개선 전 | 개선 후 |
|---|---:|---:|
| 작업 outcome의 사전 판정표 일치 | 15/15 | 15/15 |
| 코드 리뷰 verdict의 사전 판정표 일치 | 10/15 | 15/15 |
| 두 보고 모두 기존 기계 출력 파서 통과 | 9/15 | 14/15 |
| 실행 불가·분류 불가 | 0 | 0 |

위 수치는 서로 다른 기준이며 합산하지 않는다. 작업 outcome 일치가 본문의 완료 주장까지
정확하다는 뜻은 아니다. 본문 대조에서 개선 후 `unrun-1`은 필수 검증 미실행과
outcome=blocked를 쓰면서도 첫 문장에 “작업 완료(코드·단위테스트·린트 PASS)”를 사용했다.
이는 이번 목표에 대한 **잔여 실패**다. 개선 후 `failed-0`의 review는 BLOCK인데
next_skill=omc-task를 써서 기존 BLOCK 라우팅(null)과 충돌했다.

완료 outcome은 개선 전에도 모두 기준에 맞았으므로 완료 오판 감소를 입증하지 못했다.
리뷰 경계 구분의 기준 일치는 증가했지만 단일 고정 문맥 평가의 결과일 뿐이다.
사전 정의한 사례가 정답을 쉽게 드러내며, 서비스 지연·캐시·모델 변동도 통제하지 못했다.

## 증거와 후속 경계

원문·프롬프트·해시·프로토콜·개별 결과는 다음 저장소 밖 경로에 보존했다.
임시 파일이므로 장기 보존을 보장하지 않으며, before의 저장소 기준은 1f7b215다.

```text
/private/tmp/omc-completion-reporting-20261015-162028/
  before.json / after-v1.json / strict-results.json
  validation-v2/before.json / after.json / protocol.json / results.json
  validation-v2/{before|after}-{case}-{repeat}.prompt.txt
  validation-v2/{before|after}-{case}-{repeat}.answer.txt
  SUMMARY.json
```

기존 광고 비교 결과와 광고 보완 리뷰는 이번 안내 변경의 효과 근거로 소급 집계하지 않는다.
다음 검토에서는 잔여 본문·기계 출력 불일치를 다루되, 반복 지시문만으로 보장한다고
주장하지 않는다. 별도 강제 차단 엔진은 이번 범위 밖이다.

## 리뷰 후속 보완과 12회 점검

첫 상태 문장을 상태별로 고정하고, 확인된 코드 반영은 `구현 상태: 반영됨`으로
분리하도록 했다. 리뷰의 `/task`는 수동 제안이며 BLOCK 기계 라우팅의
`next_skill=null`, `user_selection_needed=true`를 덮어쓰지 않도록 명시했다.
기존 두 실패 응답 원문과 SHA-256을 `scripts/fixtures/omc_completion_reporting_failures.json`에
보존했다. 회귀 검사는 원문의 본문/기계 상태 모순과 라우팅 거부를 재확인한다.
이 검사는 새 응답을 자동 차단하는 런타임 엔진이 아니다.

후속 RED는 5 failed / 8 passed였고 관련 회귀는 131 passed다.
같은 모델과 출력 파서를 사용해 Claude/Codex 지침의 5사례를 각각 1회씩,
Claude의 미실행 재점검과 **판정이 BLOCK으로 고정된 라우팅 점검**을 1회씩 수행했다.
따라서 후속은 총 12회, 전체 평가 호출은 72회다. BLOCK 고정 사례는 판정 품질이
아닌 조건부 라우팅의 점검이며, 이전 30회와 동일한 전후 비교로 합산하지 않는다.

| 후속 지표 | 결과 |
|---|---:|
| 작업 outcome / 리뷰 verdict의 사례 기준 일치 | 각각 12/12 |
| 기존 기계 출력 파서 통과 | 12/12 |
| 상태 첫 문장의 원문 정확 일치 | 5/12 |

미실행 3회에서는 이전의 “작업 완료 + blocked” 혼입이 재현되지 않았다.
BLOCK 고정 사례도 null/true 라우팅으로 통과했다. 다만 첫 문장 규칙 전체는 미충족이다.
7건의 불일치 중 4건은 끝의 마침표 추가이며, 나머지 3건은 증거 불일치 2회와
BLOCK 고정/검증 실패 1회에서 더 일반적인 `구현됨·검증 미완료`를 선택한 것이다.
원문 일치 기준을 사후 완화해 통과로 집계하지 않았다. 이 응답들도 본문에는 구체적인
증거 차이 또는 검증 실패를 적었으나, 고정 상태의 우선순위 준수는 입증되지 않았다.

**리뷰 지적 두 실패의 이번 표본 재현은 해소 / 기계 계약 12/12 / 첫 상태 문장 검증은 미완료**다.
일반 업무에서의 재발 방지나 전체 효과가 입증됐다는 판정은 하지 않는다.
원문과 최종 지침 스냅샷은 다음 경로에 있으며 최초 평가 자료는 그대로 보존했다.
