# /task — OMC TDD 파이프라인

구현 작업을 7단계 체크포인트 양식으로 실행합니다.
**각 단계의 빈칸을 채운 후 다음 단계로 넘어갑니다. 건너뜀 금지.**

---

## 전제 조건

준비 담당이 policy 해시·session_id·run_id·basis_sha256을 고정한 비교 작업은 다음 두 명령이 모두 통과해야 기존 승인·CONTRACT로 진입합니다:

```bash
python3 scripts/omc_validation_command.py task-context --target . --sha256 <policy_sha256> --session-id <session_id> --run-id <run_id> --basis-sha256 <basis_sha256>
python3 scripts/omc_validation_command.py run --target . --profile omc-guard-task
```

불일치·누락·실패는 중단하며 세션 교체·승인 복사·기준 축소로 복구하지 않습니다. 일반 작업은 아래 Guard를 사용합니다.
비교 기록은 `.omc/comparisons/<run_id>/final-selection.json`에 씁니다. `python3 scripts/omc_validation_command.py selection-path --target .`의 반환 경로와 수집기 `compare-entry`의 기본 경로는 같습니다. 루트 기록 파일을 생성·스테이징하지 않습니다. 수집 오류는 `.omc/native-stream-errors/`에 원인과 원문 해시를 별도 보존하며 native stdout은 그대로 유지합니다. 오류 후 자동 재실행은 하지 않습니다.

```bash
python3 scripts/omc_guard.py require --for "task" --target .
```

OMC 세션 미컨펌 시 즉시 중단 → `python3 scripts/omc.py state confirm --target .`

## 완료 보고 생성 게이트

실행 기록과 native 호출 영수증은 별개입니다. 영수증이 없으면 `python3 scripts/omc_native_red_evidence.py diagnose --target .`로 읽기 전용 진단을 확인합니다. `receipts`의 배열 형식은 유지합니다. 명령은 한 줄로 단독 실행하며 끝의 `2>&1` 한 개만 허용합니다. 기록 삭제·덮어쓰기나 runner 중첩 재실행은 하지 않습니다. 최종 공식 상태는 `complete-task` 출력 그대로 사용하고, 수집 결과의 `report-comparison.txt`에서 공식 판정과 모델 원문의 상태 불일치를 별도로 확인합니다. 이 안내는 모델 준수나 실제 실행 성공을 보장하지 않습니다.


CONTRACT 등록 시 이번 작업의 필수 검증 ID를 고정합니다:
`python3 scripts/omc_pipeline_guard.py contract-done --required-checks tests,lint,browser`
브라우저가 불필요한 작업은 계약에서 제외하고 그 이유를 설명합니다. 이후 현재 작업에서 실제 FAIL을 확인하고 `red-done <테스트파일> --evidence-file <RED근거JSON>`을 등록합니다.
검증 JSON은 먼저 `python3 scripts/omc_pipeline_guard.py verification-path`로 현재 작업 폴더 내부 경로를 받아 그 경로에만 작성합니다. /tmp 등 외부 경로나 외부를 가리키는 심볼릭 링크를 사용하지 않습니다. 최종 보고 직전 `python3 scripts/omc_pipeline_guard.py complete-task --verification-file <제공받은 내부 경로>`를 실행하고 첫 상태 문장과 기계 판정을 그대로 사용합니다.
검증 JSON 형식: `{"session_id":"현재 confirmed session ID","implementation":{"status":"applied","evidence":"구현 반영 확인 근거"},"checks":{"tests":{"status":"passed","evidence":"검증 출력 위치"},"lint":{"status":"passed","evidence":"검증 출력 위치"},"browser":{"status":"unrun","evidence":"미실행 이유"}}}`.
허용 상태는 passed/failed/mismatch/unrun이며 누락·알 수 없는 상태·빈 근거는 미완료입니다. 필수 검증은 계약에 고정된 전체 목록을 확인합니다. 구현의 반영 상태·근거가 없으면 `구현 여부 확인 불가·검증 미완료`로 보고합니다. 현재 작업의 CONTRACT·RED 등록이 없거나 계약 최초 등록 이후 새로 생기거나 내용·권한이 달라진 미스테이징 구현 변경이 남으면 완료로 출력하지 않습니다. 계약 최초 등록에 보존한 기존 변경은 그대로면 제외하고, 같은 세션에서 계약을 다시 등록해도 기준을 갱신하지 않습니다. `--staged`의 신규 구현 없음은 전체 완료 증거가 아닙니다.
도구 출력 뒤 최종 답변을 다시 길게 작성하지 말고, 상태 문장을 첫 줄에 한 번만 두며 상태·다음 행동을 반복하지 않습니다. 수집자는 모델 종료 후 최종 원문 전체를 수정 없이 보존하고 서식 품질과 필수 의미 판정을 따로 검사합니다. 이 명령은 호출자가 제공한 상태·근거 문자열을 판정합니다. 실행 결과의 진위나 브라우저 실제 수행을 인증하지 않으며, 명령을 우회한 자유 응답을 물리적으로 차단하지 않습니다. 증거를 만들어내거나 완료를 위해 필수 검증 목록을 줄이지 않습니다.

## 완료 보고와 검증 경계

완료 판정 계약: CONTRACT에서 필수 검증의 대상·방법·통과 조건을 확정한다. 통제된 컴포넌트 검증과 실제 서비스 검증은 별개이며 필수 대상 대신 다른 화면·버전의 증거를 쓰면 증거 불일치다. 필수 검증 통과일 때만 전체 완료를 보고한다. 미실행·확인 불가는 구현됨·검증 미완료, 실패는 수정 필요, 증거 불일치는 재검증 필요로 보고한다. 브라우저 불필요가 계약상 명확하면 브라우저 미실행만으로 보류하지 않는다. 기존 실패는 동일 기준의 비교 근거가 있을 때만 신규 실패와 구분한다. 코드 승인과 전체 완료를 구분하며 미충족 검증·사유·다음 행동 한 가지를 명시한다. 이 안내는 물리적 차단을 보장하지 않는다. task의 필수 검증이 미충족이면 본문 완료 주장 금지, outcome=blocked 및 reason_code=verification_incomplete로 보고하고 충족한 경우에만 outcome=done을 사용한다. 검증을 수행할 수 없으면 통과로 추정하거나 필수 조건을 임의로 낮추지 않는다. 기존 기계 계약: VERDICT는 PROCEED 또는 BLOCK만 사용한다. PROCEED=>done,omc-review,false; BLOCK=>blocked,null,true (순서: outcome,next_skill,user_selection_needed). risk는 low/medium/high이고 user_selection_needed는 boolean으로 출력한다. 검증 상태 첫 문장: 최종 task 보고 첫 줄은 정확히 다음 상태 문장 하나다: 통과=필수 검증 통과·작업 완료; 미실행/확인 불가=구현됨·검증 미완료; 실패=검증 실패·수정 필요; 증거 불일치=증거 불일치·재검증 필요. 실패 > 증거 불일치 > 미실행 > 통과 순으로 판정한다. 구현 반영이 확인되지 않았으면 구현 여부 확인 불가·검증 미완료를 사용한다. 첫 줄에 괄호나 부분 완료 주장을 붙이지 않는다. blocked 보고에는 작업 완료/전체 완료/구현 완료라는 부분 완료 제목을 쓰지 말고 확인된 반영 사실은 별도 줄의 구현 상태: 반영됨으로 쓴다.



### 승인된 검증 기준 연결

CONTRACT 목록을 모델이 새로 정하지 않습니다. 사용자에게 제시해 승인받은 항목을 세션별 JSON으로 기록하고 `python3 scripts/omc_pipeline_guard.py approve-checks --file <기준 JSON>`으로 등록한 뒤 CONTRACT가 정확히 같은 ID를 참조하도록 합니다. 이 명령은 이미 받은 승인을 기록하며 승인 자체나 증거 진위를 인증하지 않습니다. 명령을 실행했다는 이유로 사용자 승인을 추정하지 않습니다.

기준 JSON은 `session_id`, 1부터 증가하는 `revision`, 요청 원문 `request`, 실제 사용자 승인 메시지를 가리키는 `approval_reference`, `checks` 배열을 포함합니다. 각 항목은 `id`, `target`, `method`, `pass_condition`, `target_version`을 명시합니다. 통제 화면과 로그인 후 실제 홈은 서로 다른 ID로 두며 실제 홈 검수를 통제 화면 증거로 대체하지 않습니다. 대상 버전은 검증할 코드 snapshot이나 commit을 식별합니다.

`python3 scripts/omc_pipeline_guard.py verification-template`의 JSON 출력을 현재 작업 내부 `verification-path`에 저장합니다. 출력의 `basis_sha256`와 항목별 `definition_sha256`, `code_snapshot_sha256`는 유지하고 실제 수행한 상태·근거만 채웁니다. 템플릿은 검증 직전에 생성하며 코드가 바뀌면 이전 passed 항목을 복사하지 않고 새 템플릿으로 해당 검증을 다시 수행합니다. 코드 스냅샷은 Git tracked 파일과 Git이 무시하지 않는 모든 untracked 파일의 경로·내용·권한을 대조합니다. 확장자로 실행 설정이나 자산을 추정해 제외하지 않습니다. `.omc` 실행 기록과 검증 기록 파일 자체는 제외합니다. Git ignored 파일·외부 의존성은 이 스냅샷의 검증 대상이 아닙니다. 스테이징 위치만 바뀌고 내용이 같으면 같은 스냅샷입니다. Git이 없는 환경은 파일 전체를 검사하되 `.git`, `.omc`, `node_modules`, `__pycache__`, `.pytest_cache` 폴더와 검증 기록 자체는 제외합니다. `target_version`은 검증 대상 설명이고 실제 코드 재사용 차단은 `code_snapshot_sha256` 대조가 담당합니다. 모든 항목의 초기값은 unrun이며 실제 실행 결과를 확인하기 전 passed로 바꾸지 않습니다. 이 해시는 기준 연결 검사이며 브라우저 실제 수행 인증이 아닙니다.

범위 변경은 변경할 항목을 사용자에게 제시해 승인받은 새 개정으로만 추가합니다. 이전 파일을 덮어쓰거나 환경 부족을 이유로 임의 축소하지 않습니다. CONTRACT를 새 개정에 다시 연결하고 이전 개정 증거는 자동 재사용하지 않습니다. 변경되지 않은 항목도 대상·통과 조건·버전 일치와 실제 증거를 확인한 뒤 새 개정 기록에 연결합니다. 기준이 없는 기존 세션은 작업물을 유지하고 편집은 허용하되 전체 완료 확정만 보류합니다.

완료 명령과 수집기는 동일한 읽기 전용 전체 판정 함수를 사용해 세션·등록·승인 기준·코드 스냅샷·미스테이징 차단을 함께 확인합니다. 최종 수집기는 호출자가 지정한 expected-outcome만 신뢰하지 않고 승인 기준·개정·개별 대상과 원문 보고를 다시 대조합니다. blocked 여부만이 아니라 실패·증거 불일치·미실행·구현 확인 불가의 정확한 상태 문장을 도구 출력과 최종 보고 모두에서 대조하며 다른 상태로 완화하거나 과장하면 통과시키지 않습니다. 기준이 없거나 완료 명령을 생략하면 비교 진입을 보류합니다. 로컬 파일 직접 변조 방지는 이 기능의 보장 범위가 아닙니다.

### 요구별 RED 근거

고정 검증 정책을 사용하는 작업은 승인 기준의 `validation_commands_policy_sha256`와 `checks.tests.validation_receipt: {"path":".omc/validation-commands/calls/<id>/receipt.json","sha256":"<실제 해시>"}`를 연결합니다. `verification-template`의 초기값은 null이며 tests 실행 반환의 receipt를 그대로 채웁니다. 완료 가드는 정책·세션·run·후보·실행 원문을 대조하고 실제 테스트 판정을 다시 계산합니다. unknown은 신규 실패로 바꾸지 않으며 passed로 승격하지 않습니다. 원문과 선언 상태가 다르면 증거 불일치입니다. 고정 정책이 없는 일반 작업은 기존 형식을 유지합니다. 픽셀 결과는 고정 실행기가 만든 manifest와 report를 그대로 사용하며 모델이 영수증을 대신 작성하지 않습니다. 해시 연결은 로컬 작성자의 정직성 인증이나 변조 방지 샌드박스가 아닙니다.

승인 기준이 있는 작업은 `red-done <테스트파일> --evidence-file <작업 내부 JSON>`을 사용합니다. JSON 필드는 `session_id`, `basis_sha256`, `test_file`(작업 루트 상대 경로), `test_sha256`(RED 실행 당시 테스트 파일의 SHA-256), `check_id`(승인 검증 ID), `case_id`(이번 요구를 실패시키는 케이스), `expected_failure`, `command`, `exit_code`, `baseline_failed_cases`, `failed_cases`, `output_file`(실제 FAIL 출력의 내부 경로), `output_sha256`입니다. SHA-256은 해당 원본 바이트로 계산하고 실제 출력은 수정하지 않습니다.

먼저 변경 전 기준의 실패 케이스를 기록하고, 이번 요구를 검증하는 테스트를 작성해 실제 실패를 실행합니다. 종료 코드1과 새 실패 케이스가 필요하며, 기존 실패 목록에 있던 케이스만으로 등록하지 않습니다. 실행 불가·수집 오류를 RED로 처리하지 않습니다. 예: baseline_failed_cases=["기존 추적 실패"], failed_cases=["기존 추적 실패","새 테두리 요구 실패"], case_id="새 테두리 요구 실패". 의미 연결과 baseline·실행 기록은 호출자가 제공하므로 가드는 실행 진위·요구사항 관련성을 인증하지 않습니다. 리뷰는 실제 출력과 이번 요청의 관계를 확인합니다. 키워드 일치나 등록 성공을 TDD 준수 증명으로 사용하지 않습니다.

등록한 JSON·출력은 보존합니다. 이후 리팩터링한 테스트 내용이 달라져도 과거 RED 기록 자체를 다시 쓰지 않습니다. 승인 개정이 바뀌면 새 근거가 필요합니다. 승인 기준 없는 legacy 편집 등록은 유지하지만 새 승인 CONTRACT의 완료 판정은 근거 없는 등록으로 통과하지 않습니다. 이전 완료·비교 기록을 소급 수정하지 않습니다.

### 폴더 링크의 스냅샷 경계

저장소 내부의 정상 폴더 링크는 링크 문자열·해석된 내부 대상·폴더 권한·검사 대상 파일 목록과 내용·권한을 함께 연결합니다. 외부 경로를 거쳐 내부로 돌아오는 링크도 거부합니다. 끊김·순환·64회를 넘는 링크 해석·Git ignored 대상·.omc/.git 실행 기록 대상 링크는 보류하며, 링크를 지우거나 검사 제외로 우회하지 않습니다. 대상 폴더 안의 일반 Git ignored 파일은 기존 정책대로 검사 대상이 아닙니다. Git 없는 환경의 의존성·캐시 제외도 유지합니다. 스냅샷은 실행 진위 인증이나 동시 파일 변경에 대한 보안 샌드박스가 아닙니다.

## 최종 보고와 작업 기록의 구분

PHASE 7 기록은 최종 답변에 붙이지 않습니다. 단계별 기록과 교훈은 작업 중 처리하고, 사용자 최종 보고는 상태·변경·검증·다음 행동만 간결하게 작성합니다. complete-task의 별도 기록을 먼저 검증하고 한글 stdout만 최종 답변에 제공합니다. 기계 판정은 불변 기록으로 보존합니다. 이 최종 보고 계약이 위 단계별 양식보다 우선합니다.


## 검증된 동일 커밋 이관의 별도 완료 경로

이 스킬의 구현 작업과 종류가 없는 기존 승인 기준은 계속 `complete-task`와 현재 작업 RED를 요구합니다.
`benchmark_maintenance` 같은 work_class나 호출자의 RED 생략 선언으로 예외를 선택하지 않습니다.
이 기능 자체를 구현·수정하는 작업도 기존 구현 경로로 검증합니다.

새 동일 커밋 이관은 최초 승인 기준에 `completion_kind=verified_commit_transfer`와 `transfer` 정책을 고정한 경우에만 별도 판정합니다.
같은 작업의 개정·보존 역할 전환으로 종류나 이관 정책을 바꾸지 않습니다.

승인 후 순서(명령의 `--target`은 격리 운영 작업 폴더이며 실제 대상은 승인된 정책에서만 읽음):

```bash
python3 scripts/omc_pipeline_guard.py --target <운영폴더> contract-done --required-checks <승인ID>
python3 scripts/omc_pipeline_guard.py --target <운영폴더> register-transfer-baseline
# 등록 성공을 확인한 뒤 별도 승인된 실제 이관 절차 수행
python3 scripts/omc_pipeline_guard.py --target <운영폴더> complete-transfer --verification-file <운영폴더내검증JSON>
```

기준 등록은 대상 HEAD가 아직 승인된 기준 커밋일 때만 1회 수행합니다. 이미 대상 커밋이면 사후 등록을 거부합니다.
이관 전후 Git 상태·원래 구현의 검증 통과·리뷰 READY·요청 범위·원본/대상 내용·권한·보존 증거를 확인합니다.
등록 중 HEAD·인덱스·보존 대상이 바뀌면 기준을 게시하지 않습니다.
정확한 대상 커밋과 단일 부모, 승인된 전체 경로, 작업 ID·대상 Git/인덱스 경로를 결속합니다.
검증 근거 없음·failed·unrun·mismatch·현재 기준 만료·범위 불일치는 RED 제외 자격이 아닙니다.
원래 구현은 기존 판정기로 통과를 확인하며 이관의 새 RED만 제외합니다.

보존 예외는 승인된 커밋 diff의 정확한 파일·인덱스 전환과, 명시적으로 승인한
`.omc/state/review-snapshots/current.json`의 유효한 새 receipt 참조뿐입니다.
기존 receipt·snapshot·검증 원문은 불변이며 새 리뷰 JSON 기록만 정해진 영역에 추가할 수 있습니다.
다른 변경·플래그 차이·넓은 임의 제외 목록·다른 작업 기준 재사용은 차단합니다.

CLI와 수집기는 동일 승인 종류·공용 판정과 실제 반환 경로를 확인합니다.
이관 절차는 CONTRACT → 기준 등록 성공 → complete-transfer 반환이며 구현 절차의 RED를 대신 실행한 것으로 기록하지 않습니다.
이관 완료는 기능·배포·실제 서비스 검증 성공을 의미하지 않습니다.
기존 BLOCK 원문은 보존하며 과거 이관을 새 사전 기준으로 소급 완료하지 않습니다.
지원하지 않는 증거·분할/희소 인덱스·링크·등록 예산 초과는 통과로 추정하지 않습니다.
로컬 해시·Git·기록은 악의적 로컬 변조나 인간 승인·실행 진위의 인증이 아닙니다.

기계 기록의 단계: stage=task. 아래 별도 기록 규칙이 이전 출력 예시보다 우선한다.

## Machine output contract
별도 기록 모드 `detached_v1`을 명시적으로 사용한다. `omc-output/v1`의 stage/outcome/risk/next_skill/user_selection_needed/reason_code·VERDICT·기존 라우팅 의미는 바꾸지 않는다. `<!-- OMC_OUTPUT: {JSON} -->`과 `VERDICT`는 내부 판정 원문에만 두고 사용자 최종 답변에 붙이지 않는다. 한글 판정·이유·검증·다음 행동만 표시한다.
먼저 `python3 scripts/omc_output_contract.py capabilities`와 `python3 scripts/omc_workflow_validation.py capabilities`로 발행자·소비자의 지원을 각각 확인한다. 실행 전에 모드·현재 작업/세션·단계·보고 ID·마감과 명시 기록 경로를 고정한다. 문맥이 없으면 `prepare --target . --stage <단계> --report-id <새ID> --budget-sec <승인된남은초>`로 현재 상태에서 새 문맥을 만들고 반환된 context/path·SHA를 호출자 실행 메타데이터에 보존한다. 숫자 예산을 임의 연장하거나 이전 보고 ID를 재사용하지 않는다.
일반 plan/review/critique/investigate/ship 선언은 내부 원문을 작업의 .omc 안에 저장한 뒤 `python3 scripts/omc_output_contract.py publish --target . --output-context <문맥경로> --output-context-sha256 <해시> --source-file <내부원문> --source-sha256 <해시>`로 발행한다. 이는 모델 선언이며 해시 일치가 검증 통과나 사용자 승인 진위를 인증하지 않는다.
실제 task 완료는 기존 `complete-task --verification-file <내부검증>`에 `--output-mode detached_v1 --output-context <문맥경로> --output-context-sha256 <해시>`를 추가한다. 이관은 승인된 complete-transfer 경로를 유지한다. 일반 publish로 완료 가드의 발행 주체를 지정할 수 없다.
사용자 최종 답변은 발행 CLI의 한글 stdout과 같은 바이트로 제공한다. 경로/해시는 사용자 답변 꼬리표 대신 호출 인자와 실행 메타데이터로 전달한다. 수집기는 명시 manifest 경로/해시·현재 상태·native 호출/반환·실제 최종 원문을 독립 대조한다. CLI 표시 검사·수집기 fixture·실제 모델의 자유 응답 준수는 별도 증거다.
업무 차단 종료 코드1도 정상 판정으로 기록한다. 전달 실패 코드2는 업무 실패와 다르다. 저장·봉인·출력 실패 시 한글 오류만 알리고 완료/승인·자동 후속·구형 fallback을 금지한다. 실패 기록도 저장할 수 없으면 stderr·종료 원문만 보존한다. 봉인 후 표시 실패를 이유로 기존 manifest나 verdict를 수정하지 않는다.
구형 legacy_inline으로 시작한 입력만 기존 parser로 읽는다. 신형 기록 누락·변조·다른 세션·모드 혼합·표시 불일치는 보류하며 구형으로 우회하지 않는다. 구형 도구에서 신형 안내를 실행할 수 없으면 호출 전에 한글 지원 불가를 알린다. 이 안내는 플랫폼 화면 숨김이나 모델 준수를 물리적으로 보장하지 않는다.
